DESENHO DA PERSISTÊNCIA
- `TenantDbContext` captura uma única identidade de tenant autenticada por escopo.
- Contexto EF não é pooled.
- Repositório de exemplo não recebe tenant_id do chamador.
- Todas as operações tenant-scoped devem passar por `ITenantTransactionRunner`.
- O runner limpa estado de sessão, define `atendee_runtime` com `SET LOCAL ROLE`, define tenant usando parâmetro SQL em `set_config(..., true)`, executa operação, salva e conclui transação.
- Papéis separados: owner, runtime, app login e migrator; app login não recebe grants diretos de tabela.
- RLS segue como segunda barreira, não como substituto de autorização da aplicação.

NÃO VALIDADO / LIMITAÇÕES IMPORTANTES
- Ainda NÃO foi executado em PostgreSQL 18.7 real: as políticas RLS, grants, bloqueio de leitura/inserção entre tenants, reutilização de conexão física e rollback seguem sem validação de runtime.
- Docker do host Windows está em modo Windows containers; não foi alterado para Linux.
- PostgreSQL 14.24 foi encontrado com serviço Stopped e Disabled; não foi iniciado nem usado.
- Não houve instalação do PostgreSQL 18, abertura de portas ou alteração persistente do servidor.
- Autenticação/MFA e implementação de produção de `ICurrentTenantContext` ainda não existem.
- A API ainda não ativa a persistência no startup.
- `tenant_notes` é somente uma fatia demonstrativa; tabelas comerciais e operacionais precisam de migrações e políticas RLS próprias.
- A GUC `app.tenant_id` é contexto, não segredo. SQL arbitrário executado sob o runtime role pode potencialmente trocar o valor. SQL injection continua sendo risco crítico; usar consultas parametrizadas, autorizações em cada operação e privilégios mínimos.
